# unifi-cleanup

Обслуживание MongoDB самостоятельного контроллера UniFi Network. Скрипт ограничивает рост истории, восстанавливает проверенные индексы после запуска контроллера, проверяет планы запросов и поддерживает минимальные пределы памяти с резервной копией и проверкой перезапуска.

Репозиторий — [skylevels/unifi-cleanup](https://github.com/skylevels/unifi-cleanup).

## Требования

- Linux с systemd и службой `unifi.service`.
- Инициализированный UniFi Network с локальной MongoDB и доступом к её служебным базам.
- Bash, Python 3.8+, оболочка `mongo` или `mongosh`.
- `flock`, `timeout`, `crontab`, `install`, `cmp`. Для настроенных почтовых отчётов нужен `mail`.
- Права root для установки, рабочих запусков и изменения параметров службы.

Комплект рассчитан на самостоятельный Network Server. Для UniFi OS, Docker и других вариантов размещения требуется проверка путей, службы и доступности MongoDB.

Исходная проверка проводилась на VMware с 4 vCPU, 8 ГиБ RAM, 2 ГиБ swap и диском 48 ГиБ. Контроллер обслуживал 253 управляемых устройства, включая 199 точек доступа и 54 коммутатора, на нескольких площадках. Использовались UniFi Network 10.0.162, MongoDB 3.6.8 с WiredTiger и Java 25. Эти сведения описывают проверенную среду, число устройств не ограничивается значением 253.

## Установка

Перед первым удалением сохраните проверенную резервную копию UniFi. Команды выполняются на сервере контроллера.

```bash
git clone https://github.com/skylevels/unifi-cleanup.git
cd unifi-cleanup
sudo bash scripts/unifi-cleanup.sh --install
```

### Доставка в изолированную сеть

На узле с доступом к исходникам подготовьте отдельный архив `unifi-cleanup.tar.gz` и передайте его на контроллер через SSH. Для этого способа нужны `scp`, `tar` и `sha256sum`. Замените `ADMIN`, `STAGING_HOST`, путь к архиву и ожидаемый SHA-256 значениями своей поставки. Контрольную сумму получите по доверенному каналу перед установкой.

```bash
(
set -e
unifi_cleanup_tmp=$(mktemp -d /tmp/unifi-cleanup-src.XXXXXX)
scp ADMIN@STAGING_HOST:/path/to/unifi-cleanup.tar.gz "$unifi_cleanup_tmp/source.tar.gz"
expected_sha256='REPLACE_WITH_TRUSTED_SHA256'
printf '%s  %s\n' "$expected_sha256" "$unifi_cleanup_tmp/source.tar.gz" | sha256sum -c -
tar -xzf "$unifi_cleanup_tmp/source.tar.gz" -C "$unifi_cleanup_tmp"
sudo bash "$unifi_cleanup_tmp/unifi-cleanup/scripts/unifi-cleanup.sh" --install
)
```

У подготовленного отдельного архива корневой каталог `unifi-cleanup/`. У архивов, скачанных непосредственно с GitHub, имя корневого каталога содержит ветку или хеш коммита. Путь к установщику должен соответствовать содержимому выбранного архива.

В изолированной сети зависимости устанавливаются заранее. После доставки комплект работает с локальными API UniFi и MongoDB. Доставка почты использует настроенный почтовый сервис.

Установщик выполняет следующие шаги.

1. Сохраняет прежние служебные файлы и root-crontab в закрытом `/var/backups/unifi-cleanup/`.
2. Запускает подготовленные файлы в `--dry-run`. Для продолжения требуется завершённый `Status: DRY_RUN`.
3. Сверяет файлы и расписание на параллельные изменения, устанавливает комплект в `/opt/` и настройки в `/etc/unifi-cleanup.conf` с доступом root.
4. Регистрирует восстановление индексов после старта UniFi, перечитывает units и проверяет индексы в `--index-only`.
5. Заменяет прямые запуски `/opt/unifi-cleanup.sh` в root-crontab одним еженедельным заданием. При отсутствии root-crontab создаётся новое задание, прочие существующие строки сохраняются.
6. Применяет помощник ресурсов. Если пределы меньше заданных минимумов и RAM достаточно, выполняются изменение конфигурации, перезапуск UniFi и проверка готовности. В конце индексы проверяются ещё раз.

Установка может перезапустить контроллер для применения ресурсов. Первое удаление истории выполняется отдельным `--apply` или по расписанию. Испытательная отправка почты при установке исключена.

Устанавливаются четыре файла.

```text
/opt/unifi-cleanup.sh
/opt/unifi-cleanup.js
/opt/unifi_tune.py
/opt/install-unifi-cleanup.sh
```

Буквальные `REPORT_EMAIL` и `REPORT_FROM` из прежнего скрипта переносятся в закрытый конфиг без исполнения старого файла. Существующий `/etc/unifi-cleanup.conf` сохраняет явные значения, включая сроки хранения. При ошибке переключения установщик пытается восстановить сохранённые файлы и расписание и выводит результат восстановления.

Откат установщика охватывает файлы обслуживания, drop-in и cron. Помощник откатывает `system.properties`, если применение ресурсов завершилось ошибкой. Успешно применённые лимиты сохраняются при последующей ошибке финальной проверки индексов.

## Режимы и расписание

```bash
sudo /opt/unifi-cleanup.sh --dry-run
sudo /opt/unifi-cleanup.sh --index-only
sudo /opt/unifi-cleanup.sh --apply
```

| Режим | Ресурсы | Индексы | История | Почта |
| --- | --- | --- | --- | --- |
| Обычный запуск, `--dry-run` | План | Проверка наличия | Подсчёт кандидатов | — |
| `--index-only` | Ожидание готовности и план | Восстановление реестра | — | — |
| `--apply` | Автоматическое повышение меньших пределов | Восстановление реестра | Удаление ограниченными партиями | При настроенном получателе |

Рабочее задание cron запускается каждое воскресенье в **03:00 по системному времени сервера**.

```cron
0 3 * * 0 /opt/unifi-cleanup.sh --apply >> /var/log/unifi-cleanup.log 2>&1
```

У очистки и восстановления индексов разные блокировки. Это позволяет `--apply` дождаться перезапуска UniFi, внутри которого запускается `--index-only`. Параллельный рабочий запуск завершается с кодом 75.

## Индексы и запуск UniFi

| Коллекция | Имя индекса | Ключ |
| --- | --- | --- |
| `ace.user` | `site_id_1_last_seen_-1` | `{site_id:1,last_seen:-1}` |
| `ace.rogue` | `site_id_1_last_seen_-1` | `{site_id:1,last_seen:-1}` |
| `ace.reference_name_history` | `delete_time_1` | `{delete_time:1}`, обычный индекс без TTL |

Подходящие индексы используются повторно. Отсутствующие создаются в фоне с повторным чтением `getIndexes()` для подтверждения. Совпадающее имя с другими параметрами приводит к ошибке. На новой установке отсутствие необязательных `rogue` и `reference_name_history` означает пропуск их проверки. Отсутствие обязательной `ace.user` требует проверить адрес MongoDB и завершение первоначальной настройки контроллера.

UniFi при запуске может удалить добавленные индексы. Установщик добавляет `/etc/systemd/system/unifi.service.d/90-maintenance-index.conf` с `ExecStartPost`. Шаг выполняет от root `--index-only` после готовности API и MongoDB, с внешним пределом 240 секунд и отдельной блокировкой. Префикс systemd `-+` оставляет ошибку шага в журнале и позволяет контроллеру продолжить запуск. После устранения причины проверку можно повторить вручную.

Регулярное обслуживание использует проверку и восстановление отсутствующих индексов. Плановые `compact`, `repair` и пересоздание уже подходящих индексов исключены.

В отдельных контрольных запросах индекс истории клиентов уменьшил время с 868 до 19 мс, индекс `rogue` — с 15 до 1 мс при лимите 100 результатов. Проверка старых имён с нулевым результатом изменилась с 581 мс и полного просмотра коллекции до нуля чтений и менее 1 мс. Это результаты конкретных запросов. Общую скорость контроллера и задержки обновления устройств оценивают отдельными замерами.

## Память и проверка перезапуска

Минимумы рабочего режима — **1024 МиБ кеша MongoDB и 4096 МиБ Java heap**. Помощник читает фактический кеш из `serverStatus`, а heap — из аргументов работающего Java-процесса через `/proc`, без JDK-инструментов. Дополнительно проверяется готовность локального API `/status` и MongoDB.

В `--apply` меньшие пределы повышаются автоматически. Используются `db.mongo.wt.cache_size=1024`, `db.mongo.wt.cache_size_default=false` и `unifi.xmx=4096` либо более высокие сохраняемые значения. Большие текущие и явно заданные пределы сохраняются. Для целевых heap и кеша резервируется ещё 1536 МиБ RAM для ОС. Для минимальных целей требуется не менее 6656 МиБ, то есть 6,5 ГиБ общей RAM.

При недостатке RAM или неподтверждённых текущих пределах помощник пропускает настройку и указывает причину в отчёте. При необходимом изменении он сохраняет закрытую копию `system.properties`, атомарно обновляет параметры, перезапускает UniFi и проверяет готовность и реальные пределы. Ошибка вызывает восстановление прежней конфигурации, повторный перезапуск и проверку. Такой рабочий запуск очистки получает `ERROR` и останавливается. Отсутствующий необязательный `system.properties` может быть создан в существующем каталоге данных инициализированного контроллера.

Режим `--dry-run` выводит план, `--index-only` использует его для ожидания готовности. Рекомендации о меньшем кеше или heap и сообщения о неизвестных значениях включаются в тело отчёта. Сами эти сообщения не означают ошибку удаления.

## Хранение и ограничения

| Коллекции | Срок по умолчанию | Параметры конфига |
| --- | --- | --- |
| `ace.user`, `ace.reference_name_history` | 1000 дней | `KEEP_USER_DAYS`, `KEEP_REFERENCE_DAYS` |
| `ace.rogue` | 180 дней | `KEEP_ROGUE_DAYS` |
| `ace_stat.stat_5minutes` | 60 дней | `KEEP_5MIN_DAYS` |
| `ace_stat.stat_hourly` | 180 дней | `KEEP_HOURLY_DAYS` |
| `ace_stat.stat_daily`, `stat_monthly`, `stat_archive`, `wifi_connection_event` | 1000 дней | `KEEP_DAILY_DAYS`, `KEEP_MONTHLY_DAYS`, `KEEP_ARCHIVE_DAYS`, `KEEP_WIFI_DAYS` |

Тысяча дней меньше трёх календарных лет. Скрипт задаёт границы своей очистки, встроенное обслуживание UniFi может удалить историю раньше. Увеличение фактически доступной истории требует отдельной настройки UniFi и оценки ресурсов.

Числовое время в секундах и миллисекундах, включая BSON Long, и BSON Date обрабатываются раздельно. Для `stat_*` используется `datetime`, для `wifi_connection_event` — `time`. Непригодные и отсутствующие временные значения сохраняются для отдельной проверки.

В `ace.user` предусмотрены условия сохранения имён, заметок, блокировок, фиксированных IP и точек, сетевых назначений, переопределений, 802.1X и нестандартных групп. Управляемые устройства исключаются из кандидатов. Перед удалением выбранной партии повторно проверяются возраст, сайт и условия сохранения. Число удалений по сайтам берётся из подтверждённого результата каждой партии.

| Ограничение | По умолчанию |
| --- | --- |
| `BATCH_SIZE` | 500 записей |
| `MAX_PER_COLLECTION` | 10 000 удалений за коллекцию |
| `MAX_TOTAL` | 50 000 удалений за запуск |
| `MAX_RUNTIME_SEC` | 600 секунд цикла удаления |
| `QUERY_TIMEOUT_MS` | 5000 мс ограниченной выборки |

Процессы помощника ресурсов и MongoDB имеют раздельные внешние пределы по `MAX_RUNTIME_SEC` с запасом на завершение. Достигнутый предел отражается как `LIMIT`, оставшиеся кандидаты могут быть обработаны следующими запусками. При ошибке уже подтверждённые удаления остаются в отчёте.

## Конфигурация и показатели отчёта

Рабочие параметры находятся в `/etc/unifi-cleanup.conf`. Используются локальный адрес MongoDB, порт 27117 и локальный `/status`. При другом размещении доступны `MONGO_HOST`, `MONGO_PORT`, `MONGO_SHELL`, `UNIFI_STATUS_URL` и `UNIFI_PROPERTIES`. Изменение этих параметров требует проверки соответствия поддерживаемой схеме размещения.

Почтовый отчёт включается заполнением `REPORT_EMAIL`, необязательный `REPORT_FROM` задаёт отправителя. Например, в своей конфигурации можно указать `ops@example.org`. Отправка выполняется только при `--apply`, отказ передачи письма возвращает ненулевой код.

Поля отчёта зависят от выбранного режима. Полный подсчёт и очистка показывают все следующие показатели.

| Группа | Показатели |
| --- | --- |
| Запуск | Режим, начало, завершение, длительность цикла в секундах, итоговый статус |
| Коллекции | Число кандидатов в `--dry-run` или подтверждённых удалений в `--apply`, срок хранения, используемое временное поле, подтверждённые удаления до ошибки |
| Сайты | Количество кандидатов или удалений по каждой коллекции и сайту, итог по сайту, общий итог запуска |
| Размеры до и после | Логические данные, выделенное хранение и индексы, в МиБ |
| Контрольный запрос по каждому сайту | Лимит до 100 результатов, время в мс, число результатов, просмотренных документов и ключей, выбранный индекс |
| Индексы | Уже подходящий, созданный и подтверждённый, отсутствующая необязательная коллекция, ошибка параметров или результата |
| Ресурсы | Фактический максимум кеша MongoDB и heap Java в МиБ, минимумы 1024/4096 МиБ, план изменения, достаточность RAM, пропуск с причиной, результат применения или восстановления |
| Неизвестные значения и ошибки | Неподтверждённые пределы, рекомендации при значениях ниже минимумов, причины ошибок MongoDB, помощника и почты, коды завершения процессов |

Логический `dataSize` и выделенное хранение имеют разный смысл. Освобождённые блоки WiredTiger могут использоваться повторно, поэтому уменьшение логических данных не следует считать измерением возвращённого дискового места.

| Статус | Значение |
| --- | --- |
| `DRY_RUN` | Подсчёт и план завершены |
| `OK` | Рабочий проход завершён |
| `LIMIT` | Достигнут предел, остаётся проверить отчёт и объём кандидатов |
| `ERROR` | Ошибка процесса, настройки или выполнения с ненулевым кодом завершения |
| `INDEX_OK` | Реестр индексов проверен в `--index-only` |

## Проверка работы

```bash
sudo /opt/unifi-cleanup.sh --dry-run
sudo /opt/unifi-cleanup.sh --index-only
sudo crontab -l
sudo tail -n 100 /var/log/unifi-cleanup.log
sudo journalctl -u unifi --no-pager -n 100
```

Для повторной установки используется `sudo /opt/unifi-cleanup.sh --install`. Резервные копии настроек, журналы, данные MongoDB и рабочие адреса отчётов хранятся на контроллере в закрытом доступе.

JavaScript-сценарии также можно запустить отдельно одной из доступных оболочек.

```bash
node tests/unifi_cleanup_cases.js
```

Тесты используют временные файлы, фиктивную базу и заглушки служб и почты. При отсутствии Node и `mongo` соответствующий автоматический JS-тест пропускается, его отдельный результат учитывают вместе с отчётом Python-тестов.
